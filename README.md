# NamaSetu

**NAMASTE ↔ WHO ICD-11 (TM2 + Biomedicine) terminology bridge with explainable matching and FHIR R4 output.**
Problem Statement SIH25026 (Ministry of Ayush) · Team Byte Strong · Chandigarh University

> **Status: Milestone 7 (polish).** Everything through Milestone 6, plus: one Patient workspace (timeline,
> interaction checks and diagnosis coding with that patient as the FHIR subject), safe typo correction for typed
> terms, faster mapping, a latency benchmark, an accessibility pass and refresh-token fixes. Deployment is next.
> This README is completed in Milestone 8 with generated metrics.

> ⚠️ Research / decision-support prototype. Not a certified medical device. Mappings require clinician validation.

## Quick start (Docker)

```bash
cp .env.example .env        # optional: every key has a safe default
docker compose up --build
```

- UI: http://localhost:5173 (the header shows **MOCK** and **SAMPLE DATA** when no keys are set)
- API docs: http://localhost:8000/docs
- Health: http://localhost:8000/health

## Local mode (no Docker)

Requires Python 3.11+, Node 20 and GNU make.

```bash
make dev-local     # SQLite + in-process tasks + MOCK ICD-11/ABHA; /health reports DB_MODE=sqlite-local
```

## Data (SAMPLE — illustrative, not official)

Bundled in `backend/data/sample/`. Every code carries a `SAMPLE-` prefix, so none can be mistaken for a real NAMASTE or WHO code.

| File | Contents |
|---|---|
| `namaste_sample.csv` | 53 Ayurveda conditions (48 disorders, 5 patterns) + 11 groups, each with IAST, Devanagari, English gloss, definition, parent, type |
| `icd11_tm2_sample.json` | TM2-style hierarchy: disorders and patterns, index terms, 8 illustrative WHO-index biomedical links |
| `icd11_bio_sample.json` | 23 biomedical entities across 9 chapters |
| `synonyms.yaml` | English / IAST / Devanagari / Hinglish variants for every condition, plus 46 Sanskrit root terms |
| `gold_mappings.csv` | 53 reference NAMASTE→TM2 mappings, fixed seeded 80/20 split (42 train / 11 test) |
| `embedded_db.json` | All of the above in one file, the seed for LOCAL mode (`make embedded` regenerates it; CI checks it is in sync) |

Every ingest creates a versioned, checksummed **DatasetRelease**. Re-ingesting identical data is a no-op. A changed
release records a diff (added / removed / changed codes, biomedical links) and flags affected approved mappings for
re-review. Every ingest is written to an append-only, SHA-256 hash-chained audit ledger, and database triggers
reject UPDATE/DELETE on it. `GET /audit/verify` recomputes the chain and reports the first broken link.

**Real data.** NAMASTE exports (CSV/XLSX) load through a configurable column map (`NamasteColumnMap`; the defaults
follow the `NAMC_*` header layout). WHO ICD-11 loads LIVE when `ICD_CLIENT_ID`/`ICD_CLIENT_SECRET` are set
(OAuth2 client credentials, API v2, disk cache, retry/backoff). See `.env.example` for the chapter and TM2 settings.

## Matching engine

Six stages: deterministic baseline → normalisation/transliteration → lexical + char n-gram → semantic →
hybrid ranker → confidence gate. Every candidate carries the Explanation Object (per-stage scores, matched
terms, root terms, hierarchy path, entity-type check, template reasoning). Details: [docs/matching.md](docs/matching.md).

`make index` retrains the ranker on the gold train split and prints its calibration. Latest run on SAMPLE data:

| Item | Value |
|---|---|
| Training | 42 train-split queries, grouped 5-fold CV top-1 = 1.0 |
| Calibrated thresholds | T_HIGH = 0.50, T_LOW = 0.45 |
| Absent-answer queries suppressed | 97.6% (41 of 42) |

## FHIR R4

Base URL `/fhir` (`application/fhir+json`; errors are OperationOutcome). Real responses are in
[docs/fhir-examples/](docs/fhir-examples/). Latest check: **17/17 files, 0 errors** in the official HL7 Validator
(FHIR 4.0.1, NRCeS `ndhm.in` 6.5.0 loaded). See [docs/standards.md](docs/standards.md) for exactly what is and
isn't conformant. Note that the NRCeS Condition profile currently allows only ICD-10 / SNOMED CT codings, so it is
not claimed.

## Medications (reference only — not a prescription)

SAMPLE data: 17 Ayush formulations and single herbs, 17 biomedical products, 15 brand rows and 35 cited
condition links (2 pending review). Every row cites a source; SAMPLE citations say "verify against source" rather
than inventing page numbers.

- **Where to see them:** **Medications** on any result card shows Ayush formulations (composition, botanical names,
  parts used, proportions as printed) and biomedical products (salts with strengths, Schedule and NLEM badges,
  brand examples). Biomedical products appear only when an approved biomedical link exists.
- **Medicines page** ("What's inside this medicine?"): brand, salt, generic, formulation or herb, in any script.
  The check list warns on duplicate salts.
- **Brand matching:** exact, or a unique 1–2-character typo. Unknown brands return "Brand not found".
- **Safety by design:** no dose regimen fields exist anywhere. Processed metals and minerals get a "qualified
  supervision" badge, and interaction checking arrives in Milestone 5B.

## Medication history and interaction warnings

- **Synthetic patients:** 10 SYNTHETIC patients (fake names, TEST ABHA-like IDs) come with multi-encounter history,
  imported through the same FHIR path as real uploads.
- **Line resolution:** lines like "Tab Glycomet 500 BD" or "Mulethi churna" resolve deterministically, by brand,
  then product or formulation, then salt or herb. Anything else is "Unrecognised — please verify".
- **Active window:** only medications active on the chosen date are checked. A stopped medicine never raises an
  "active" alert.
- **Alerts:** every alert shows both agents, the full path (e.g. *Nisha Amalaki Churna → contains herb Haridra →
  constituent Curcumin × salt Glimepiride*), severity, evidence level and citation.
- **No false "all clear":** an empty result reads "No interaction found in the loaded dataset (vX)", never
  "no interactions".
- **Access and privacy:** clinicians and admins only. History text is never logged; the ledger records counts.
  History is exportable (`/fhir/Patient/{id}/MedicationStatement`) and deletable per patient.
- **Measured:** line resolution, interaction and duplicate-salt precision / recall, brand and ingredient-name
  resolution are in the generated evaluation block above and in [docs/eval-results.md](docs/eval-results.md).
  The medication gold sets were written by the team, so these figures show the pipeline works; they are not
  independent accuracy.

## Dashboard, evaluation runs and exports

- **Dashboard** (`GET /dashboard`): codes ingested, approved mappings, pending review, no-match, approved biomedical
  links, band distribution, 14-day queue throughput and the latest evaluation. The pitch-deck "mapping gap"
  (7,340 / 1,941 / 529) is shown labelled as official figures cited in the pitch deck; NamaSetu does not compute it.
- **Evaluation runs:** `POST /eval/run` (admin, background task) stores an `EvalRun` with the dataset releases and
  model version; `GET /eval/runs`, `/eval/runs/latest`, `/eval/runs/{id}`. The Docker API container stores a
  first run on its first start; `make eval-db` stores one for the configured database.
- **Exports:** `GET /export/{json|csv|pdf}?kind=mappings|decisions|audit` returns small exports directly; larger
  ones (and `POST /export/jobs`) run as background jobs with a download link. Each file's header carries the
  generation date, dataset releases, the disclaimer and the SAMPLE label.

## Sign-in and roles

**The website has no sign-in screen.**
- **Menu.** It opens straight on Search. The menu has Search, Medicines and Mapping (the AYUSH ↔ WHO ICD-11 crosswalk).
- **Login.** The **Login** button opens the Care portal, which has the Hospital, Doctor and Patient sign-ins.
- **Demo session.** Behind the scenes, the frontend signs in as the sandbox `clinician` account. To use another account, set `VITE_DEMO_USERNAME` / `VITE_DEMO_PASSWORD` when you build the frontend. A production API creates no demo accounts, so this session fails there.

The API still enforces the roles below. The older pages (review queue, audit ledger, admin, patient history, Consultation, Evaluation and Dashboard) remain in the codebase but are not routed in this build. The evaluation still runs from `scripts/run_eval.py`, and its results are in `docs/eval-results.md`.

| Role (shown in the UI as) | Can | Sandbox demo login |
|---|---|---|
| clinician (Clinician (doctor)) | search, review / approve / override, add biomedical links, build Conditions, ingest Bundles, patient history and interaction checks | `clinician` / `Clinician@NamaSetu1` (or ABHA mock `dr.demo@sbx`, OTP `123456`) |
| coder (Medical records officer) | search, map, send to review | `coder` / `Coder@NamaSetu1` |
| admin (Administrator) | everything, plus ingest, thresholds, users | `admin` / `Admin@NamaSetu1` |
| viewer (Viewer (read-only)) | read-only | `viewer` / `Viewer@NamaSetu1` |

### Consultation and crosswalk

- **Consultation** (`/consultation`, clinician or admin) puts the whole workflow on one screen:
  - the synthetic patient's current medicines, decoded into active salts;
  - an AYUSH diagnosis and its NAMASTE → ICD-11 TM2 → ICD-11 biomedicine mapping from the engine, with confidence, band and reasoning;
  - the clinician-approved formulation links for that diagnosis;
  - herb–drug screening of those formulations against the patient, with cited alerts.
- **Crosswalk** (`/crosswalk`, every role) lists every published mapping in one table. The table joins the two FHIR ConceptMaps (`namaste-to-tm2` and `tm2-to-biomedicine`).

### Care portal (demo)

`/care-portal.html` is a standalone page (one HTML file, `frontend/public/care-portal.html`, in-memory state,
fictional data) with separate Hospital, Doctor and Patient sign-in. It shows that a patient's record follows
their ABHA ID across two hospitals:

- A doctor opens an unassigned patient only with the patient's QR token or consent OTP. That access lasts
  30 minutes, is read-only for history and reports, and is shown in the patient's access log.
- Hospitals see their doctors and patient names only.
- Doctors issue a printable final report showing the salt of every medicine, with duplicate-salt and
  allergy warnings.
- Insurance eligibility (demo rules) is shown for each diagnosis, treatment and prescription, based on its
  coding system (ICD or AYUSH) and the patient's policy dates. All rules live in one `INSURANCE_RULES` object.
  Every check a doctor runs is written to the patient's access log.

The demo credentials are in a collapsible panel on the page. Reloading the page resets all data. The page loads
one external script: qrcodejs 1.0.0 from cdnjs, pinned with an integrity hash.

These sandbox passwords apply only outside production. In production, demo accounts are created only when
`DEMO_<ROLE>_PASSWORD` is set, and startup refuses the default `JWT_SECRET`. Policy lives in one place
(`backend/app/core/rbac.py`).

The login, map and search endpoints are rate-limited. Every action is written to the hash-chained ledger under the
signed-in user.

**Review queue:**

- **What gets queued:** MEDIUM results are routed in automatically. Coders can send any suggestion. On seed, every
  code without an approved mapping is queued (11 with SAMPLE data).
- **Decisions:** approve, approve as wider/narrower, choose another or manual search, or reject. A comment is
  mandatory for any override, and keyboard triage is supported (`j`/`k`, `a`, `w`, `n`, `r`).
- **Effect:** approvals create a new mapping version (the old one is superseded), with a Provenance record and a
  ledger entry, and flow straight into the ConceptMap, `$translate` and Condition output.
